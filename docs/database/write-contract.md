# 写入流程与接入边界

日期：2026-11-02。SQL是结构约束，事务服务是命令入口；不能让页面直接更新余额或随意切换posting_state。本文件是接入契约，未修改应用代码。

## 统一入口

新增、编辑、删除、导入、校准和恢复由同一数据层调度写操作。使用项目兼容的RDB事务接口，明确提交/回滚与错误处理；不混用事务对象、独立连接和未等待的异步写入。

每个命令验证输入、执行数据库事务、检查受影响行数，成功后才发布UI状态。错误必须向上返回，不能因某条SQL使用ABORT就假设整个业务事务已自动回滚。**任何步骤失败都由事务服务回滚完整命令。**

## 新增账目

1. 校验UUID、合法币种版本、最小单位整数及范围；校验日期与IANA时区、偏移和保存的本地日期一致。SQLite只能验证日期格式，不负责解析来源文件的时区。
2. 校验账本、分类和账户当前可用；新记录不能选已归档项。历史记录是否可编辑归档项由命令区分，不能只依赖下拉列表过滤。
3. 计算优惠和实付。需要折算时用精确运算取得book_minor；用户/账单确认的实际结算金额为准。收支没有必要的汇率就返回待处理，不能补1或0。转账两侧的结算金额与换算依据必须完整；本金不参与收支统计，本位币book_minor允许为空，不为无关的第三币种报价阻断本来完整的转账。
4. 开始单个数据库事务；创建draft账目、资金变动、汇率快照和关联。普通支出/收入允许不使用账户；转账必须两侧完整且账户不同。
5. 更新posting_state为posted，触发发布校验。关联手续费在同一命令事务内完成，失败时本金和手续费一起回滚。
6. 检查本命令所有应发布记录确已posted，再提交。禁止把draft作为另一个可持久保存的用户草稿功能。

SQL中的draft是为保证多行创建顺序而设的内部中间态。单条SQL无法声明“到COMMIT时不得存在draft”；因此完整事务服务是必须实现的部分。

## 编辑与删除

2026-11-05：同币种CNY支出编辑已按下列契约接入，详情和实现范围见[账目详情与编辑](../development/entry-detail-edit.md)。不执行表结构迁移；其它币种/FX及收入编辑仍未接入。

- 编辑先按`id AND revision=expected`进入draft并递增revision，检查受影响行数必须为1；为0说明数据已变，返回冲突并重读。
- 在同一事务内更新账目、资金变动及FX快照，重新发布并提交。变化时间必须同步更新资金腿；修改本位币金额必须更新相符快照。
- SQL视图会在提交后的新状态反映净差，不再额外执行一次“余额减金额”，避免重复扣款。
- 导入身份和balance_mode不可在普通编辑中修改。preserve记录修改金额、账户、备注和删除，仍不影响余额。
- 普通删除只设置deleted_at_ms并递增revision；恢复时核实原关联仍有效。转账本金与关联手续费需要按用户明确选择整组处理，不留半侧资金变动。
- 归档账本/账户不撤销历史余额。删除账本要显式处理账目和预算，删除有历史的账户先处理关联或归档，不能用删除主数据来隐藏资金影响。
- 原始表仅供数据层内部使用，业务列表与统计读取v_posted_transactions等视图，避免读取未提交导入批次或draft。

## 初始余额与校准

创建账户与唯一opening调整、其资金变动在一个事务内完成；初始为0也保存opening作为明确基线。发布校准时SQL会核对before_minor是否仍等于当前余额，过期快照被拒绝。

校准只保存固定差额。后来改旧账会改变当前余额，不重新计算校准事件来抵消用户编辑。已发布校准不能更新/删除；撤销以新的calibration记录并指定reversal_of_id，delta必须与原调整相反，before/after则使用撤销时的实际余额。

## 导入

解析和分批staging不进入业务查询。按用户确认的字段与值映射生成有效行，JSON按配置版本解析、限定大小和结构；不执行文件中的公式，不输出原始财务内容到日志。

最终确认时：

1. 重验目标账本、所有选中行及重复保留决定。核对selected+skipped=total，并确认跳过行为。
2. 开始一个数据库事务，批次转committing，写confirmed_at；按行创建draft账目，其balance_mode等于批次选定值，import_row_id唯一。
3. 写资金变动、快照和关联，发布所有选中记录。随后标记批次committed并记录计数和时间；业务视图只在此状态下暴露导入记录。
4. 提交。任一步失败整体回滚，单独记录失败状态不能意外提交先前的部分账目。
5. 重试前查询批次，已committed直接返回原结果；不能把唯一约束报错当成导入成功，也不能换一组新UUID重新重复导入。

对大文件必须设容量限额并测试事务耗时；如果将来需要分批业务提交，需要重新设计部分成功与撤销语义，不能沿用“失败全部撤回”的现有界面。

## 精度、统计与字段校验

- 写入单值限制在安全整数范围；SQL金额检查拒绝REAL。汇率TEXT只做基础格式检查，规范化、运算、舍入与数值比例校验由域层负责，不能将展示汇率当作实际金额的唯一依据。
- 聚合读取使用精确整数/字符串路径；getLong超出ArkTS安全整数时不能直接转number。SQLite64位SUM溢出必须报错或分批精确累计，不允许转REAL/TOTAL“修复”。
- 净资产先按currency_id分组，再选择统一估值时间和报价换算。缺价或舍入差额要可解释，不能直接跨币种相加。
- name_key由域层做固定、版本化的Unicode规范化与大小写处理，不依赖SQLite默认NOCASE支持所有语言。
- 首版预算按月。域层校验月首至下月月首及有效期间规则；SQL只验证合法且有序的日期区间及完全相同区间唯一，不宣称已禁止任意重叠区间。
- 手续费、报销实际回款、退款、分摊等按已确认范围处理；group_id不是完整交易组外键，整组删除/保存由事务服务保证。

## 文件、备份与迁移

数据库ready附件状态不能证明文件已存在、写完整或未被外部损坏；附件服务须在发布前执行路径、内容、大小、hash校验，失败回滚关联，孤立文件延迟清理。

完整备份/恢复按model-v1.md中的数据库与不可变附件共同快照执行。正式迁移前仍须给出持久化执行范围、备份、回滚和真机验证方式并获得执行授权。

schema-v1.sql针对空库评审，不使用IF NOT EXISTS掩盖结构漂移。接入时用版本化迁移器执行完整SQL语句，不能用简单分号split切断触发器正文；先验证外键已启用，再开始业务写入。本轮未设置应用user_version，也未初始化真实dataset_id或货币字典。
